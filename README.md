# HW7: JSONB, GIN-індекси та time-series features у PostgreSQL

Домашня робота на синтетичних даних: робота з `JSONB` (оператори `@>`, `?`, `?|`, JSONPath), порівняння планів `EXPLAIN (ANALYZE, BUFFERS)` до і після GIN-індексу, JSONB проти нормалізованої таблиці, а також lag / rolling / expanding features на часових рядах.

## Інструкція запуску

1. Встановіть залежності (Python 3.10+):

   ```bash
   pip install pixeltable-pgserver sqlalchemy psycopg2-binary pandas jupyter
   ```

2. Запустіть Jupyter та відкрийте ноутбук:

   ```bash
   jupyter notebook hw7.ipynb
   ```

3. Виконайте комірки зверху вниз (`Run All`). Ноутбук сам:
   - піднімає локальний PostgreSQL через `pixeltable_pgserver` (дані зберігаються в `./temp`);
   - виконує SQL-скрипти з `sql_cmnds/` через допоміжні функції `sql_exec` / `sql_reader`;
   - у кінці зупиняє сервер (`db.cleanup()`).

> Окремо встановлювати PostgreSQL не потрібно. Запускати ноутбук потрібно з кореня репозиторію, бо шляхи до SQL-файлів відносні (`sql_cmnds/...`).

## Таблиці

### `t7_hw_events` (`sql_cmnds/jsonb_table.sql`)

Сирі події користувачів: 50 000 рядків, 5 типів подій по 10 000 кожного. Дані повністю детерміновані: генеруються через `generate_series(1, 50000)` без `random()`, тому результати відтворювані.

| Колонка      | Тип           | Опис і спосіб отримання                                                                   |
|--------------|---------------|-------------------------------------------------------------------------------------------|
| `event_id`   | `INTEGER` PK  | `GENERATED BY DEFAULT AS IDENTITY`, автонумерація                                         |
| `user_id`    | `INTEGER`     | `(n % 1000) + 1`, 1000 користувачів                                                       |
| `session_id` | `UUID`        | `md5(((n / 10) % 5000)::TEXT)::UUID`, одна сесія охоплює кілька подій                     |
| `event_ts`   | `TIMESTAMPTZ` | `2024-04-01` мінус `n % 60` днів, діапазон у 60 днів                                      |
| `event_type` | `TEXT`        | `n % 5` по колу: `page_view`, `click`, `add_to_cart`, `checkout`, `recommendation_shown`  |
| `country`    | `TEXT`        | цикл по `UA, PL, DE, US, GB, FR`                                                          |
| `payload`    | `JSONB`       | структура залежить від `event_type` (див. нижче), будується через `jsonb_build_object`    |

Структура `payload` за типами подій:

| `event_type`           | Ключі `payload`                                                       |
|------------------------|-----------------------------------------------------------------------|
| `page_view`            | `url`, `referrer`, `device`                                           |
| `click`                | `element_id`, `page_url`, `device`                                    |
| `add_to_cart`          | `product_id`, `price`, `quantity`, `tags` (масив)                     |
| `checkout`             | `order_id`, `total`, `items_count`, `payment_method`                  |
| `recommendation_shown` | `model_name`, `model_version`, `recommendations` (масив), `experiment` |

Індекси, які створює ноутбук у розділі GIN-demo:
- `idx_t7_events_payload_gin_pathops`: GIN (`jsonb_path_ops`) по `payload` для `@>` та JSONPath;
- `idx_t7_events_device_btree`: B-tree по виразу `(payload ->> 'device')` для рівності за конкретним ключем.

### `t7_hw_checkouts_norm` (`sql_cmnds/norm_table.sql`)

Нормалізована версія checkout-подій: 10 000 рядків. Створюється командою `INSERT ... SELECT` з `t7_hw_events` (`WHERE event_type = 'checkout'`), ключі з `payload` розкладаються на типізовані колонки.

| Колонка          | Тип              | Джерело                                                    |
|------------------|------------------|------------------------------------------------------------|
| `event_id`       | `INTEGER` PK     | `event_id`                                                 |
| `user_id`        | `INTEGER`        | `user_id`                                                  |
| `event_ts`       | `TIMESTAMPTZ`    | `event_ts`                                                 |
| `order_id`       | `TEXT`           | `payload ->> 'order_id'`                                   |
| `total`          | `NUMERIC(10, 2)` | `(payload ->> 'total')::NUMERIC(10, 2)`                    |
| `items_count`    | `INTEGER`        | `(payload ->> 'items_count')::INTEGER`, `CHECK (> 0)`      |
| `payment_method` | `TEXT`           | `payload ->> 'payment_method'`, `CHECK IN ('card', 'paypal', 'crypto')` |

Додатково створюється індекс `idx_t7_checkouts_norm_pm` по `payment_method`.

### `t7_hw_taxi_daily` (`sql_cmnds/com1.sql`)

Синтетична щоденна статистика поїздок таксі по зонах. Це вхідна таблиця для побудови lag, rolling та expanding features. 5 зон × 60 днів = 300 рядків, діапазон дат `2024-02-01` … `2024-03-31`. Первинний ключ `(pickup_zone_id, ts_day)` гарантує рівно один запис на зону й день без пропусків, тому віконні функції працюють по регулярному ряду.

| Колонка          | Тип              | Спосіб отримання (`n` = 0…59 — номер дня, `zone_id` = 1…5)       |
|------------------|------------------|-------------------------------------------------------------------|
| `pickup_zone_id` | `INTEGER`        | `CROSS JOIN` з `VALUES (1), (2), (3), (4), (5)`                   |
| `ts_day`         | `DATE`           | `DATE '2024-03-31' - (59 - n)`                                    |
| `trip_count`     | `INTEGER`        | `500 + n*7 + zone_id*50 + (n % 5)*30`: тренд + зональний зсув + «тижнева» хвиля |
| `avg_fare`       | `NUMERIC(10, 2)` | `12.5 + zone_id*0.7 + (n % 4)*0.4`                                |
| `total_distance` | `NUMERIC(12, 2)` | `1500 + n*25 + zone_id*120`                                       |

Усі формули детерміновані: лінійний тренд (`n*7`, `n*25`), різний рівень для кожної зони та короткі періодичні коливання (`n % 5`, `n % 4`). Завдяки цьому lag-, rolling- та expanding-ознаки легко перевірити вручну.

### `lag_features.sql` і `comb_view.sql`

- `lag_features.sql`: будує lag, rolling та expanding ознаки поверх `t7_hw_taxi_daily` за допомогою віконних функцій (`PARTITION BY pickup_zone_id ORDER BY ts_day`).
- `comb_view.sql`: комбінований view, що збирає результат в одному місці для подальшого використання.
